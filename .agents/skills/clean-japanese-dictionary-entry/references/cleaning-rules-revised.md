# 词条清洗规则

## 提交契约

最终对象只允许以下顶层字段：

```json
{
  "id": 1,
  "words": ["半額"],
  "kana": "はんがく",
  "tone": "⓪",
  "detail": [
    {
      "type": "名词",
      "meanings": [
        {
          "zh": "半价；规定金额的一半",
          "examples": [
            {
              "jp": "子どもは半額です",
              "zh": "儿童半价。"
            }
          ]
        }
      ]
    }
  ],
  "rome": "hangaku",
  "description": "半价；金额的一半",
  "ai_source": "chatgpt-5.6"
}
```

硬性限制：

- id 必须与 GET 返回值一致，且为正整数。
- words 必须是非空字符串数组；去除首尾空白、空字符串和完全重复项。
- detail 必须是非空数组；每个有效 detail 至少包含一个有效 meaning。
- meanings 中只保留 zh 和 examples，禁止 jp。
- examples 中只保留 jp 和 zh，禁止 read、voice 及其他字段。
- 不输出 null 义项或空对象。没有可靠例句时 examples 可以为空数组。
- kana、rome、description 最长 255 个字符，tone 最长 100 个字符，ai_source 最长 50 个字符。
- 输出必须是标准 JSON 数据，不得包含注释、Markdown、证据字段或置信度字段。

## 字段规则

### words

- 保存词典中可独立作为该读音词头的规范词形，不要加入解释、括号、声调符号或活用形式。
- 多个词形必须共享本词条的读音和主要义项。读音不同的同形词应是其他词条。
- 顺序优先保留原有主词形在前，只在明确错误时调整。
- 有可靠且常用的汉字表记时，将汉字表记作为主词形。假名表记只有在现代日语中具有独立且常见的书写习惯，或被词典明确列为常用表记时才保留。不得仅因为可以写成假名就机械加入假名形式。
- 对能稳定与 `する` 结合构成サ变动词的名词，`words` 只保留名词或词干部分，不保留 `する` 及其活用形式。名词用法与サ变动词用法表达同一核心含义时，不强制拆分 `detail`；只有含义、使用条件或搭配方式明显不同时才拆分。具体类型按 `type` 规则处理。
- 外来语使用日语中的标准片假名词形。

### kana

- 使用该词条的标准词典读音，不插入空格、罗马字或声调符号。
- 和语通常使用平假名；片假名词及惯用片假名表记可保留片假名。
- 必须和 words、例句中的实际用法一致。无法确认特殊读音时保留原值。

### tone

- 本项目使用圈数字表示东京式声调，例如平板型为 `⓪`，头高型可能为 `①`。
- 每个词条只允许一个 `tone` 字段，字段类型必须是字符串，不得输出数组或其他结构。
- 一个词通常只保留一个可靠且主要的东京式声调。
- 同一标准读音确实存在多个可靠的东京式声调型时，应全部保留在同一个 `tone` 字符串中，并使用全角中点 `・` 连接，例如 `⓪・③`。
- 多个声调型应按照原始数据或可靠词典中的顺序保留，并删除完全重复项。
- 只把明确的同形 OCR 字符规范成 `⓪①②③④⑤⑥⑦⑧⑨⑩`，不得猜测缺失的声调编号。
- 当前值为空且没有可靠词典证据时保持空字符串，不得输出 `null`，也不得依据汉字、假名长度、拍数或个人语感推算声调。
- `tone` 表示词条标准词形单独发音时的东京式基本声调，不记录例句中因助词、活用或复合结构产生的临时声调变化。

### type

- `type` 表示当前 `detail` 对应的词性或语法类型，必须与同级 `meanings.zh` 和 `examples` 的实际用法一致。
- 优先沿用项目现有的中文词性体系，例如：
  `名词、代名词、数词、形容词、形容动词、副词、连体词、接续词、感叹词、助词、助动词、接头词、接尾词、助数词、动词、自动词、他动词、自他动词、サ变`
- 本次审核不为了全库命名统一而机械改写原有标签；但新增或纠正 `type` 时，必须优先使用项目中已经存在的固定名称。
- `type` 不得自行创造同义标签、缩写或混用不同写法。例如，不要混用：
  `他动词、他動詞、他五、五段他动词`
- 同一词条具有多个彼此独立的词性，且各词性下的含义、搭配方式或使用条件明显不同时，应拆分为多个 `detail`。
- 多个词性或语法属性表达同一核心含义，且用法紧密相关时，可以在同一个 `type` 中使用全角中点 `·` 连接，避免生成释义完全重复的 `detail`。
- 组合 `type` 必须按照项目规定的固定顺序书写，不得随意交换顺序或无限叠加。

例如：

```text
名词·形容动词
名词·サ变
名词·自动词·サ变
名词·他动词·サ变
名词·自他动词·サ变
```

- 普通动词主要记录动词词性和可靠的自他属性，推荐使用：
  `动词、自动词、他动词、自他动词`
- 能确认是动词，但无法可靠判断自动词或他动词时，使用 `动词`，不得猜测自他属性。
- 自动词、他动词和自他动词应以稳定用法、原始数据和可靠词典知识为依据，不得仅凭中文释义、个人语感或单条例句判断。
- 不得仅根据单条例句中的助词 `が` 或 `を` 判断整个词条的自他属性；`を` 也可能表示经过场所、离开点等，并不必然证明该词是他动词。
- 同一词形确实同时具有自动词和他动词用法时，使用 `自他动词`，不得强行归入其中一种。
- 当前清洗不要求也不主动补充五段、一段、カ变等活用类别，不得为了补全信息而根据词尾自行推断。
- 原数据已经包含五段、一段、カ变等信息时，只有该信息明确可靠且项目确实需要保留时才可继续使用；存在疑问时，应改用较宽泛的 `动词、自动词、他动词或自他动词`，避免错误的活用分类干扰学习者。

- 对能够稳定与 `する` 结合构成动词的词条，应保留 `サ变` 属性，因为 `words` 中只保存词干，不保存带 `する` 的形式。
- サ变词条的 `words` 只保存名词或词干部分，例如：
  - `勉強する` 保存为 `勉強`
  - `確認する` 保存为 `確認`
  - `運動する` 保存为 `運動`
- 不得在 `words` 中保留：
  `勉強する、勉強をする、勉強します、勉強した`
- `kana` 和 `rome` 也只对应去除 `する` 后的词干。
- サ变词条根据可靠程度使用：
  `名词·サ变、名词·自动词·サ变、名词·他动词·サ变、名词·自他动词·サ变`
- 无法可靠判断サ变动词的自他属性时，使用 `名词·サ变`，不得猜测。
- `サ变` 在本项目中主要表示该词可以接 `する` 构成动词，不要求同时补充五段、一段等其他活用分类。
- 不得机械地为所有名词添加 `サ变`。只有自然日语中能够稳定与 `する` 结合，并且有原始数据、可靠词典知识或有效例句支持时，才可保留 `サ变` 属性。
- 不得仅因为中文释义中出现“做、进行、实施、开展”等词，就判断该词属于サ变。
- サ变义项的例句允许出现 `する` 的自然活用形式，例如：
  `確認する、確認します、確認した、確認している、確認される`
- 当名词用法和サ变动词用法表达同一核心含义时，可以合并在同一个 `detail` 中，使用组合 `type`。已有可靠例句时，可以分别保留能够证明名词用法和动词用法的例句，但不得为了证明两种用法而强行新增例句。

例如：

```json
{
  "type": "名词·他动词·サ变",
  "meanings": [
    {
      "zh": "学习；用功",
      "examples": [
        {
          "jp": "毎日の勉強が大切です",
          "zh": "每天的学习很重要。"
        },
        {
          "jp": "大学で日本語を勉強しています",
          "zh": "我在大学学习日语。"
        }
      ]
    }
  ]
}
```

- 当名词用法与サ变动词用法的实际含义、搭配方式或使用条件明显不同时，应拆分为不同的 `detail`，不得为了减少 `detail` 而强行合并。
- `する` 本身作为独立词条时单独处理，不适用“去除 `する`、只保存词干”的规则。
- 拟声词、拟态词、古语、口语、俗语、书面语、敬语、方言和专业领域等属于词汇类别、语体或使用范围，不得代替实际词性写入 `type`。

### meanings.zh

- 使用简体中文，表达该词在当前词性下的真实含义，而不是逐字翻译日文构词。
- 每个 meaning 表示一个可区分义项；同义重复项合并，使用条件明显不同的义项分开。
- 删除与词头、读音或词性明显无关的串条内容。
- 不因义项罕见就删除。冷僻、古语或专业义项需要当前例句、OCR 或可靠知识支持。
- 不新增仅由联想得到的含义，也不把例句的临时语境提升为词典义项。

### examples

- 优先使用现代日语中自然、常见、简短且能独立理解的例句。不得为了模仿新闻、影视或文学作品而生成复杂、引用式或具有特定背景依赖的句子。
- 例句必须直接证明所在 meaning，不能只和主题相关。
- 中文应准确翻译整句，避免漏译否定、时态、数量、敬语和语气。
- 修正明显 OCR 错字、假名误识别和中日文错配。无法可靠修复的例句应删除。
- 优先保留和修正已有短例句。新增时使用常见、简短、无争议的表达，通常每个义项 0 至 3 条即可。
- 不要为凑数量生成重复句、含义模糊的句子或不自然的书面表达。
- `examples` 中的例句必须与当前 `examples` 同级的 `zh` 释义相关。

### rome

- 使用小写 ASCII 罗马字，并沿用项目现有的 Hepburn 风格。
- `rome` 必须与 `kana` 明显对应，不得混入假名、汉字、声调符号、空格或解释性文字。
- 长音、促音和拨音按照项目现有词条的转写习惯处理；在项目尚未确定统一细则前，不得在单次清洗中自行切换到另一套合法转写体系。
- 只修正与 `kana` 明显不一致的拼写。仅因存在多套合法罗马字写法，不应无依据改写原值。

### description

- 用简洁简体中文概括最终保留的主要义项，便于列表展示和搜索，不得多次出现中文意思重复的义项。
- 不加入日文定义、例句、审核说明、来源或置信度。
- 应与 detail 一致；detail 删除义项后同步删除 description 中对应摘要。
- 不得将冷门、偏僻义项写入 `description`，以免误导学习者；即使这些义项保留在 `detail` 中，也不应进入 `description`。

## 字段独立修正与决策矩阵

审核必须逐字段进行。一个字段缺少证据时，只保留该字段原值；不得因此放弃其他字段的明确修正，也不得把局部未知升级成整条词条的问题。

按以下顺序决定提交类型：

| 审核结果 | 决策 |
| --- | --- |
| 至少一个业务字段存在高置信修正，修正后整体一致 | `submit_changed` |
| 没有高置信修正，原对象整体合理且可安全提交 | `submit_unchanged` |
| 关键字段存在无法消除的互斥冲突，保留局部原值或删除坏数据仍无法形成安全一致结果 | `submit_original_with_issue` |

执行要求：

- “存在未知字段”不等于“无法审核”。未知字段保留原值，其他字段照常复审和修正。
- 空 `tone` 是合法值。没有可靠证据时保持 `""`；不得猜测，也不得仅因此记录问题。
- 已确认 `kana` 后，`rome` 的空格、大小写或明显转写错误应正常修正。
- 能明确映射到项目类型体系的非规范 `type` 应正常修正。
- 可以安全删除的错误义项、重复义项和坏例句应直接删除；删除后仍能满足提交契约时，不属于重大不确定性。
- OCR 没有收录完整复合词、短语、专名或机构名，只表示辅助证据缺失。应继续依据词形、读音、结构一致性、可靠日语知识和有效例句审核。
- 不得用“多数关键字段看起来支持同一答案”来覆盖少数关键字段。只要不同字段组分别组成两个合理词条身份，就必须按下文的“词条身份分裂”处理。

示例：

- `博士課程 / はかせかてい / tone: ""`：确认标准读音为 `はくしかてい` 后，修正 `kana` 与 `rome`，声调仍保持空，使用 `submit_changed`。
- `期間中 / きかんちゅう / kikan chuu / tone: ""`：若其余字段可靠，将 `rome` 修正为项目采用的无空格形式，使用 `submit_changed`。
- 某个例句明显属于其他词条：删除该例句；只要剩余词条仍完整一致，就使用 `submit_changed`。

## 重大不确定性与跳过提交

审核结果先在内部归类为 `submit_changed`、`submit_unchanged` 或 `submit_original_with_issue`。三类都生成提交对象；第三类保留原始业务字段并另行记录问题。

`submit_original_with_issue` 是最后手段，必须同时满足以下两项：

1. 冲突涉及 `words`、`kana`、核心词性、主要义项或当前同形同音词条身份，并存在两个或更多合理但互斥的结论。
2. 依据当前数据、可靠日语知识和清晰辅助证据仍无法消歧，且通过保留不确定字段、采用较宽泛但正确的类型、删除坏义项或坏例句，仍无法形成安全一致的提交对象。

### 词条身份分裂

以下结构性冲突直接满足重大不确定性的双重门槛：

- `words` 与 `kana` 共同指向词条 A，而 `rome`、主要义项或全部例句共同指向不同的词条 B。
- 词形与读音可以组成一个真实词条，但主要义项和例句可以组成另一个真实词条；修正任何一组都等于替数据库决定原本要保存的目标。
- 动词词干、名词词形或完整动词形式混在同一记录中，现有字段无法确认哪一种才是目标词头。

遇到词条身份分裂时：

1. 不得按字段数量进行多数表决。
2. 不得仅凭通用日语知识认为某个候选“更像正确答案”。知识只能确认候选成立，不能确认记录的目标身份。
3. 不得把一部分字段改成另一部分字段对应的候选。
4. 必须保持七个业务字段原样，返回 `submit_original_with_issue`，并在原因中分别写明两组字段各自指向的候选。
5. 只有用户明确指定目标，或可信上游依据能够直接确认该记录目标身份时，才可修正后使用 `submit_changed`。

例：

- `words=金子、kana=かねこ` 指向姓氏“金子”，而 `rome=kinsu` 与“金钱、金币”主要义项指向 `きんす`。即使 `きんす` 是成立的日语词，也不能证明数据库目标一定是它；自动审核必须原样提交。
- `words=建、kana=けん`，而 `rome=tate` 且例句全部是 `建てる` 的动词用法。目标可能涉及 `建`、`建て` 或 `建てる`，自动审核必须原样提交。

在同时满足上述两项的前提下，以下情形可判定为 `submit_original_with_issue`：

- `words`、`kana`、核心词性或主要义项之间存在实质冲突，无法依据当前词条、本规则、可靠日语知识和清晰的辅助证据消除。
- 同一关键字段存在两个或更多合理但互斥的结论，选择任一结论都可能明显误导学习者。
- 数据发生严重串条、截断或结构损坏，需要大规模重新编造词形、读音、主要义项或例句才能满足提交契约。
- 无法确认内容是否属于当前同形同音词条，继续修改可能把另一个词条的词性或义项合并进来。
- `xmj.txt` 与当前数据在关键内容上发生明确冲突，OCR 上下文又不足以确认哪一方正确，并且该冲突无法通过保留局部原值形成安全一致结果。OCR 单方面未命中不属于冲突。

以下情况本身不构成重大不确定性：

- `xmj.txt` 没有命中、命中乱码或只提供弱证据。
- 当前 `tone` 为空且没有可靠声调证据；保持空字符串即可。
- 只有声调缺失或声调证据不足，但词形、读音、词性和主要义项可以可靠审核。
- 完整复合词、短语、专名或机构名未被 OCR 收录。
- 仅凭词条是组合表达、专名或“不像普通单词”而怀疑其有效性。
- `rome` 存在空格、大小写或可根据已确认 `kana` 直接修正的拼写问题。
- `type` 标签不规范，但能明确映射为项目已有的正确类型。
- 对非关键细节没有额外证据，但原值合理且可以安全保留。
- 无法确认是否需要增加冷僻义项；此时不增加该义项即可。
- 例句不可用但可以安全删除，并允许保留空的 `examples`。
- 没有发现需要修改的内容；完整复核后可使用 `submit_unchanged`。

声调单独存在不确定性时，优先保留原值或空字符串并继续审核。只有当前非空声调很可能错误、可靠来源又给出无法消解的互斥结论，并且保留它会明显误导学习者时，才可把声调列为重大冲突；此类情况必须在问题原因中明确写出相互冲突的依据，不能只写“无法确认声调”。

判定为 `submit_original_with_issue` 时，生成保持原始业务字段不变的 API 请求体，只增加 `ai_source`。向总控流程返回：

```json
{
  "decision": "submit_original_with_issue",
  "word_id": 1,
  "reason_code": "major_uncertainty",
  "uncertain_fields": ["kana", "type"],
  "reason": "词形对应两个互斥读音，现有数据与 OCR 均不足以完成消歧。",
  "issue_log_required": true
}
```

上面的控制字段禁止提交到 Agent API。`reason` 保持简短，只说明冲突，不输出推理过程或置信度分数。总控流程提交原始业务字段成功后，必须通过 `log-issue` 在项目根目录为该词条写入独立问题文件；无论问题文件是否最终写入成功，都继续处理队列，并在完成报告中统计日志失败。
